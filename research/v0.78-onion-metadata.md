# v0.78 — Onion metadata as a puzzle channel

## Verified observations

- The preserved Liber Primus onion7 `index.html` uses HTML `<title>133</title>`, wraps the page list in `<div id="331">`, and serves exactly 58 images named `0.jpg` through `57.jpg`.
- A preserved 2014 onion response carried the custom HTTP header `X-Cicada: 3301`; the associated hex payload was 256 bytes.
- A 2013 onion stage set cookies named `167` and `761`; both are prime and the names reverse into one another.
- The 2013 recruitment stage explicitly instructed candidates to build a TCP server, expose it as a Tor hidden service, and send the onion address/port through GPG-encrypted email.

## Interpretation

Tor was not merely transport. Cicada repeatedly used source/protocol/application layers as challenge-bearing surfaces: HTML title and element IDs, HTTP headers, cookies, TCP behavior, onion addressing, and PGP authentication. This makes it legitimate to test whether LP2 depends on a selector, initial state, or key artifact supplied outside the rune ciphertext itself.

## Working rule

Do not freely mine every onion number as a key. Require recurrence across independent stages, or a predeclared mapping, before promoting it. Candidate values with existing puzzle support remain 29, 58, 133, 167, 331, 761, 1033, and 3301, plus the Page32 Fibonacci/prime-index structure.

## Next attack

Build a chronological inventory of every preserved onion-layer datum (HTML metadata, custom headers, cookies, ports, filenames, payload sizes, timestamps) and test those values as selectors/initial-state controls against LP2 rather than as unconstrained additive keys.
